## 1. 默认通配监听

**确认并修复产品缺陷。** 标准库本地 TCP/UDP fixture 绑定动态端口并限制到 `lo`；分别强制双栈和 IPv6-only 后，`/proc` 在两种情况下都呈现 `::`。一个真实覆盖 IPv4 通配的 socket，原先会在 Inspect 的逐字比较及运行时额外监听检查中被拒绝。新实现只在同一网络命名空间中取得内核对该 socket 的 `INET_DIAG_SKV6ONLY=0` 后，接受 `::` 为期望的 `0.0.0.0`。该事实按地址、端口、协议及 inode 与 PID 的 FD 对照；FD 在采样末尾重新核对。生产运行时还核对 Supervisor 身份和 Unix API 对端 PID。监听匹配在 [Endpoint.Matches / Inspect](../../agent/internal/mihomo/evidence.go) 与 [exactSockets](../../agent/internal/runtime/apply.go) 共用。

| 本地观测 | 判定 |
| --- | --- |
| 原生 IPv4 通配 | 对相同端口、协议的 IPv4 通配成立 |
| IPv6 通配且内核证实 `v6only=0` | 可证明 IPv4 通配；不能代替某个具体 IPv4 的精确绑定 |
| IPv6-only、无该属性、IPv4-mapped、不同协议或别的 PID | 均不能证明该 IPv4 通配。等价的 IPv6 数字拼写可匹配 |
| UDP 已连接，或发送时自动分配本地端口 | 不计作固定入口；UDP 候选还要求内核证实显式端口绑定 |

依据 Linux [INET_DIAG UAPI](https://github.com/torvalds/linux/blob/master/include/uapi/linux/inet_diag.h) 和 [内核 socket 诊断实现](https://github.com/torvalds/linux/blob/master/net/ipv4/inet_diag.c)。[sockdiag_linux.go](../../agent/internal/mihomo/sockdiag_linux.go) 只读取本机诊断，没有用全局 `bindv6only` 或可连通性推断所有权。缺内核诊断、读不完整、网络命名空间不一致、inode 无法关联时，所需事实仍未得到；候选不会 Verified。UDP 内核元数据不能区分特意绑固定端口的业务角色，完整 Verify 仍要求独立业务证据。这个可选字段只出现在 Agent 内部检查证据，不改变控制协议、结果 DTO、schema 或迁移。

**真机仍待证：** T02 的初始通配发布没有保存 FD/inode、socket family 属性和具体失败阶段；不能倒推当时失败一定由双栈比较引起。明确 IPv4 的历史阳性不验证默认通配、多网卡或新的 Linux 诊断依赖。真实 Mihomo 监听形态及 Ubuntu/Alpine 的默认运行权限仍需在新构建集成时核对。

## 2. 到期处理与观察器

**状态机边界获本地证据，原观察器的结果丢失。** [expire / confirmRestrictions](../../agent/internal/runtime/restriction.go) 在持久 checkpoint 中记录单调时钟、墓碑和源任务的 pending 结果，随后取消进行中的操作并触发内核协调。[apply](../../agent/internal/runtime/apply.go) 按过滤后配置应用、核对监听，按 Listener ID 清理选定存量会话，再要求真实 Revocation 才确认。若恢复在确认写入时发现新到期，R02 将 `errRestricted` 保持为回退 pending 并唤醒协调，避免竞争窗口被记成普通不可恢复失败。

本地测试使用确定性时钟推进应用时间、真实 AEAD checkpoint 和可控 Kernel/Process。结果：显式撤销在重载前已持久，随后另一授权到期能取消长重载；取消结果没有确认时间，恢复后两个身份都按各自原始授权记 confirmed，保留身份配置未改。既有长 Fetch、时钟倒退/重启、旧产物不复活、探针失败与 pending 回执前后测试也通过。[Controller 测试](../../controller/internal/releases/releases_test.go) 独立验证记录事务失败不给 receipt，pending/乱序/重复/非原授权证据不会提前放端口，真实匹配的 confirmed 入库后仅释放对应端口。这里的会话验证是可控边界和源码复核；它不代表实机保留的原连接已经通过回显。

**观察器最小修复建议（未改 T02 草稿）：** 每个探测尝试先持久写出结构化记录，再由断言读取。至少写入 `attempt_id`、逻辑端点/身份、`fresh|existing`、`phase`（连接、SOCKS 协商、CONNECT、收业务回显）、`outcome`、可用的数字 `errno` 或 `socks_rep`、是否与随机业务载荷匹配及时间；不写凭据、载荷原文或私有配置。禁止用宽异常捕获把所有情况映射成 `socks_failed`。

| 实际观察 | 判定 |
| --- | --- |
| 业务响应与载荷完全匹配 | `forwarded`；对已到期身份为明确失败 |
| 已建立并曾回显的原连接收到 EOF/reset | `closed`，只证明这条原连接关闭 |
| 新连接到已确认归属的目标入口明确 `ECONNREFUSED`，或有绑定目标/阶段的明确协议拒绝 | `refused`，记录依据；SOCKS 回复保留数字 REP，规则拒绝与连接拒绝各有语义，不单凭本地 SOCKS 的回复归因为远端凭据被拒 |
| 超时、探针启动/协商失败、未知归属、通用 SOCKS 失败、收到不匹配业务字节 | 独立记 `timeout`、`probe_error` 或 `unexpected_reply`，均不足以确认拒绝 |

正式补验应为新连接拒绝单独生成可溯源证据，同时保留另一身份原连接的业务回显、入口/PID 变化和 pending → confirmed → released 顺序。Alpine Controller / Ubuntu Agent 原案仅证实旧连接关闭和另一身份同一连接回显；`fresh_old` 实际值未保存，不能认定旧凭据仍可用，也不能认定它已被明确拒绝。

## 3. 端口冲突、回退与 REJECT

**确认并修复空配置回退误报。** [restore](../../agent/internal/runtime/apply.go) / [rollbackFailure](../../agent/internal/runtime/execute.go) 使用当前 Startup（最近一次确认的快照），核对已认证产物和落盘渲染，再用当前账本过滤、Validate、应用和核验。PreviousGood 保留上个确认来源，不能绕过当前 Startup 校验或以旧授权代替失败的恢复。旧逻辑只在可继续使用当前 Verified 指针时接受已确认的空配置；候选应用尝试已经清空该指针，导致完全一致的空 Startup 重启并检查后还被报回退失败。现在以已确认 Startup 的精确渲染摘要及空监听为依据，先经实际应用和监听核验，存在待清理项还要通过撤销证据。候选仍是 Failed，未变成发布成功。

独立 checkpoint fixture 从已验证旧版出发，模拟候选 Mihomo API 接受但监听缺失。旧版可恢复时为 confirmed，Candidate/Applied/Verified 回到经验证 Startup；旧版也缺监听时为 failed，无确认时间，受控进程停机，清除未确认的 Candidate/Applied/Verified，保留 Startup/PreviousGood。已有确认的空 Startup 另有回归。新增脱敏诊断区分 API 所有权未就绪、socket 检查失败、期望监听缺失、覆盖未知和集合不符；真实回退失败另记阶段，避免只有 `rollback=failed` 终态。

**驱动问题 / 仍待证：** Ubuntu Controller / Alpine 下游的候选冲突与 rollback failed 是已观察事实；当时旧业务是否恢复未知，本地可控状态机不证明该次故障成因。另一拓扑先前用例提前退出，后续省略仍在账本的授权且未提交 tombstone；`DEPENDENCY_IN_USE` 符合 [B04 依赖护栏](../../controller/internal/releases/artifact.go)，不改护栏。未来用干净旧基线分别测实际 OS 冲突、旧业务回显和真正不可恢复的分支，核对非本平台监听和必要端口仍保留。实际 REJECT 没有改成 DIRECT，未获得正向业务证据也不能报转发 Verified；本轮不重跑真实 REJECT 业务。

## 4. 缺/错 key、坏 checkpoint 与进程保护

[composeRuntime](../../agent/internal/agent/runtime.go) 先构造 Supervisor；checkpoint 或 key 错误由其退出分支尝试 Stop 并保留原错误。核对 [Supervisor](../../agent/internal/runtime/process_linux.go) 的 boot ID、PID/start time、可执行设备/inode、argv、每次启动 token 及 pidfd。R02 收紧已记录 PID 的判定：若身份核验失败，只有确知旧进程已退出或 start time 明确不同，才当作原槽位无人；`/proc` 不可读、缺 start 或同 start 但身份不一致时返回失败且不发信号。

本地使用固定版 Mihomo 空 REJECT 配置，仅打开私有 Unix API；每种故障独立启动 fixture。子进程通过普通 CLI 的 `command.Execute` 错误/退出路径调用 composeRuntime，不访问入网或 Controller。分别采集进程退出码、stdout、stderr 和原进程 pidfd 状态，并逐字节比对故障后的密文，恢复 fixture 的正确材料验证 checkpoint 可重新打开。未换节点密钥、未覆写产品状态。

五个独立用例的退出码均为 1，stdout 均为 0 字节，原因均在 stderr。缺 key 报 `runtime checkpoint key unavailable`，错 key 和坏密文报 `CHECKPOINT_INVALID_OR_WRONG_KEY`，三者的已确认受管 PID 均退出；token 不匹配时另报 `AGENT_KERNEL_PROCESS_FAILED`，模拟记录 start time 与活 PID 不符时两者均无停机，原 fixture 在验证后恢复记录并按确切身份清理。全部故障保留原故障态密文字节。第一遍 fixture 未要求空配置完成启动，不能用于证明停机；终检在注入前要求私有 Unix API 已可用。

T02 的 Alpine Agent 错 key 只留下错误串，缺流归属与停机证据；坏检查点没走到。历史 Ubuntu 阳性及本轮本机证据均不能补写 Alpine 结论。

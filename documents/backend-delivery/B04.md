## 接口与运行顺序

```go
releases.NewRepository(db storage.Database) *releases.Repository
releases.New(repo *releases.Repository, cipher secretstore.Cipher,
    guard adminauth.Guard, options releases.Options) (*releases.Service, error)

type Options struct {
    Now           func() time.Time
    NewID         func(string) (domain.ID, error)
    Deliver       func(context.Context, control.Command) error
    Connected     func(domain.ID) bool
    RemovalIntent func(context.Context, domain.ID) (enrollment.RemovalIntent, error)
}
type Plan struct {
    Kind     domain.TaskKind
    Subject  domain.RevisionRef
    Deadline time.Time
    Nodes    []NodePlan
}
type NodePlan struct {
    NodeID           domain.ID
    ExpectedRevision domain.Revision
    Template         control.Bundle
    DependsOn        []domain.ID
}
```

- 复用一次 `storage.Open` 的 Store 构造 Repository。用 B01 Cipher、Guard 及 B02 enrollment 的 `RemovalIntent` 构造 Service。启动接线中先声明 B02 Server 变量，Options 的 `Deliver` 和 `Connected` 通过闭包读取该 Server。将同一 Service 注入 B02 Server 的 `Results`、`Recovery`、`ArtifactResolver`、`Artifacts`，完成构造后再调用 `Run(ctx) error`。`Close() error` 取消并等待实现退出。应先停止调度，之后关闭控制通道及 Store。单个 Service 只启动一次，启动失败由组合根处理。
- `Submit(ctx, mutation, plan) (domain.TaskAccepted, error)` 只供可信内部编译调用。Mutation 的 ExpectedRevision 是提交者提供的 Subject revision 前置条件，须等于 Plan.Subject.Revision。逐节点使用实际 `nodes.revision` CAS，Template 目标修订须为 ExpectedRevision+1，epoch 须为当前节点 epoch。B04 按节点和依赖 ID 规范化完整请求，涵盖截止时间、模板和全部依赖。事务外重新绑定真实 task ID、调用根 `control.EncodeBundle` 并加密，单次短 Write 再核对节点/epoch/CAS/截止时间/幂等，原子写入 task、target、DAG、资源引用、预留和产物。同 key 同请求可取得原 task，包括原任务已过期，变更内容返回 IDEMPOTENCY_CONFLICT。
- 编译使用根 Bundle 格式 1 及其 B03 输入校验。支持独立 Listener、四种受限协议、DIRECT/REJECT、受限 DNS、组件 Pin 以及根允许的仓储引用。多节点 Plan 表示独立节点配置包及 DAG。格式 1 仍缺多跳代理、出口链和 Relay 映射表达能力。空 Listener 目标只用于有明确 tombstone 的撤销或清理类动作。暂无公共 Publish 路由。
- `Resolve(ctx,node,task) (control.ArtifactKey,error)` 与 `Open(ctx,node,key) (io.ReadCloser,error)` 都校验授权节点、armed 目标、当前 epoch、权限、依赖和截止时间。Open 在事务外用 B01 Cipher 解密，核对实际字节 SHA-256 及 1 MiB 上限，再在 Write 复核授权、固定最初授权来源并登记已提供下载。产物在独立表用 `Binding{Ref: artifactID, Purpose: "release_bundle"}` 封装。常规 DTO 只有任务与逐节点状态，输入包、密文和 Agent 错误详情仅在各自受限路径使用。
- 首次写明调度所有权后才调用 B02 `Deliver`。按持久任务顺序在每个节点上串行，DAG 依赖须有对应有效修订的下游确认。发布依赖需要 Applied+Verified，阻断条件包括节点失配、epoch 改变、已知墓碑或已到期的纳入授权。仅清理的空配置可凭实际清理结果结束该清理目标。断线保留待同步，失败投递间隔至少 10 秒，成功写入连接后等待结果，首次 Hello 才允许恢复重投。每次调度读最多 100 个候选并合并唤醒，后台每秒兜底检查到期。较早任务在另一节点失败时，仍为尚无结果的 armed 目标保留到原命令截止时间的串行屏障。截止时间后保留迟到结果事实，任务终态保持。
- `RecordResult(ctx,node,result) (bool,error)` 校验 mTLS 认证节点 ID、真实 task/node/target revision/digest、sequence 和证明。全部已见序号持久记录规范 JSON 摘要及安全结果字段。同序号同内容返回 false/nil，新记录在事务提交后返回 true，异内容返回 IDEMPOTENCY_CONFLICT。B02 照原接口在成功返回后发精确 receipt。较旧序号仍写历史。Restriction 另存完整结构化字段，验证最初已提供下载的真实来源、身份/监听/代次、到期时间、撤销授权及 epoch；可追加至终态。有效摘要排序使用观测时间及同来源 sequence，独立于 publish 投影。
- `Hello(ctx,node,hello) error` 核对 B02 已入库的每条 pending 结果摘要、节点所报的 artifact revision/digest 和 epoch。已知但落后的状态写 pending，首次 Hello 唤醒待恢复目标。未知摘要/修订、尚不可领取的目标或超前 epoch 记 conflict；B02 随后结束该连接。Hello 不授予 cleanup 或 Verified。100 条及整帧 1 MiB 仍由原传输契约约束。
- 强类型 Listener 派生 listener、entry、identity、credential 及 TLS/REALITY 材料引用，额外 Resources 再按 Kind/ID/Revision 落关系行。身份材料不可变，同 entry 的新代次须单调增加。引用减少以 `(reference_id, operation_id)` 唯一记录；零引用仍持有预留。已确认的逐身份 Restriction 或经过 mTLS 且与明确 tombstone 目标绑定的清理结果，才允许释放无活跃引用的端口。包含保留 Listener 的清理目标还须 Applied+Verified。回收时也检查 002 现有 `listener_references`。B04 预留按节点、端口、外层 TCP/UDP、IP 和 wildcard 冲突判断，:: 保守占双栈；固定端口冲突返回 PORT_IN_USE。
- 调度通过 B02 RemovalIntent 识别管理节点撤销。被移除节点自己的端口转 pending_cleanup，旧身份无投递和下载权限。已发布关系中的同路由 peer 保留持久链接。只有仍在线授权、有明确最新已验证模板且 Listener 未被另一条无关发布线路使用的 peer 才创建独立 cleanup task。离线和受共享约束的链接保持待处理。父任务原节点仍 pending，peer 成功不能确认父节点。Reverse/Relay 映射及尚无关系行的上游业务清理由对应业务模块提供关联。

## 管理接线与 I02 契约

`ManagementHandler() http.Handler` 实现 `GET /api/v1/tasks`（limit 默认 50，最多 200，cursor 是上一页最后 task ID）、`GET /api/v1/tasks/{task_id}` 和 `POST /api/v1/tasks/{task_id}/{cancel,retry,rollback}`。读走 Guard.Read，写走 Guard.Write 并使用现有 Mutation JSON。HTTP 写的 `expected_revision` 是源 task 账本修订。取消只限未 armed 且不含限制意图的 queued 发布/回滚。Retry 仅适用失败、超时及取消的仍为最新目标的 B04 task。主动 rollback 选指定的已成功 B04 发布/回滚任务作历史内容输入，保留组件 Pin，过滤永久撤销/到期身份，按当前每节点 revision/epoch 重新编译为新 task、目标修订和新摘要。Retry 和 rollback 使用新的 5 分钟截止时间，同一动作 key 重放返回同一任务。已有阶段一任务可读，动作返回明确 501。缺资源、截止时间、CAS 和幂等冲突分别返回相应 domain 错误。B02 公共产物路由按现有规则把内部授权失败映射为 403。

- `Hello.applied_digest` 对应其 Applied revision 的 Controller artifact digest；受本地过滤影响的 rendered digest 仅走 `Restriction.effective_digest`。如果 Agent 要额外报告当前渲染摘要，可在 `internal/control/message.go` 与 `controller/api/control.schema.json` 增加可选 `Hello.effective_digest`，保留 `applied_digest` 的 artifact 语义及旧端兼容处理。
- 首次 Open 成功提交但响应在 Agent 记录 Grant 之前中断时，现有消息无法判断 Agent 是否已记下初始 Grant。B04 可重投原任务。原任务已经终态且未验证时，拒绝用另一个 task 重新发同一不确定身份，以避免改变离线证据绑定。若 I02 后续解除这类重试限制，需协同定义 Agent 已持久 Grant 的确认，建议在 Result 增加可选 `grant_origins`（最多 128 项，字段 `identity_id`、`generation`、`origin_task_id`、`origin_target_revision`、`origin_target_digest`，节点由 mTLS 和 Result 绑定）。Controller 要复核各来源已授权、字段和目标精确匹配，再允许更新 tentative 绑定。涉及控制消息两端及 schema，当前 B04 未改共享契约。
- B05 对命令清理的 `cleanup=confirmed` 应覆盖该目标内需清理的明确 tombstone，并以实际配置移除、旧认证拒绝、存量会话清理为前提。逐身份离线限制仍通过原 Grant 来源的 Restriction 单独上报。若运行时只能确认 tombstone 的真子集，应保持命令结果 pending，并发送已有逐身份证据。
